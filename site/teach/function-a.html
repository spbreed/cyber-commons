◴Before the session

One week before

  • Send the setup email: install Git and Python 3.10+, clone the repo, install the Claude desktop app, sign in.
  • Point under-18 learners at A0.0's age guidance — broadly 13 is the floor and 18 the default, and between the two a parent or guardian sets the account up. For a class, one adult account or a local model beats thirty sign-ups.
  • Ask every learner to run the doctor and reply with its last line: python3 scripts/doctor.py, or python scripts\doctor.py on Windows.
  • Dry-run every lab. Note any output that differs from this page and correct scripts/exercises/trainer_a.py.

Day before

  • Install the application's dependencies on your demo machine: python3 -m pip install -r cybertravels/requirements.txt. This also brings in PyJWT, which A1.3 and A1.4 need.
  • Confirm ./cybertravels/run.sh serves http://127.0.0.1:8000. A1.7's human-gate demo needs it; run it as a trainer demo if learner machines struggle.
  • Print the nine-word guess sheet: one page, nine blank rows, columns word and guessed file.
  • Record a screen capture of each lab's output as a fallback for learners whose setup fails.

In the room

  • Projector on the lesson index.
  • Pairs, not solo. One driver prompts Claude, one checker compares output against this page. Swap each module.
  • A visible parking lot for questions that belong to Functions B–F.

0:15–0:45 · Setup and the nine words

Learners leave with Claude running the repo and a written guess for where each of the nine agent parts lives. The sheet is collected now and marked in Module 4.

Paste this once at the start, so Claude knows how to behave for the whole course:

A0.0Set up your computer — what this is, who it is for, and the model every lesson runs on15 min

Key idea

A skill is a written procedure (SKILL.md) the model follows. The document and the instruction are the same bytes, so learners can read exactly what runs.

Prompt to Claude

Run scripts/doctor.py and explain each ok / FAIL / -- line to me.
Then run scripts/lesson.py A0.0 and tell me exactly what happened.

Expected output

The doctor ends with a "ready" summary; -- lines are fine. lesson.py either completes and names the model, or stops with "no model configured". Both are correct.

Teach the stop. If it stops, celebrate it. The program refused to invent an answer, and that is the first security behaviour of the day.

Per operating system. The page gives Windows and Mac their own lines throughout. On Windows the command is python, not python3, and typing python3 opens the Microsoft Store.

Debrief question

Zero contract violations means the answer had the right shape. Does it mean the answer is right?

Answer. No. Shape is not truth.

Lab. Set your computer up from nothing, run one skill and read back which model answered, then find your role's row and the lesson it starts at.

A0.1Nine words for an agent — harness to multi-agent, and where each is built10 min

Key idea

Each of the nine is a component to a builder and an attack surface to an attacker.

Prompt to Claude

Explain the nine words (harness, memory & state, RAG, MCP, skills, guardrails,
evals, A2A, multi-agent) as if to a beginner, one line each, using a
travel-booking example. Do not tell me which files they live in.

Expected output

Nine one-line explanations and no file names. The lesson's own exercise is six numbered steps on paper, and it tells learners to write a question mark where they have no idea.

Say why they are guessing. Six of the nine files do not exist on their computer yet — runtime.py, memory.py, identity.py, observability.py, mcp/internal_server.py and a2a/protocol.py get created across Modules 1–3, by them. There is nothing to look up.

Talk track — how they stack. The harness is the agent. Memory, RAG, MCP and skills feed context in. Guardrails sit on the way out and are the only one that says no. Evals sit beside it. A2A and multi-agent are several harnesses at once.

Debrief question

Every arrow into the harness is a way for text you did not write to reach the model. Which of the nine worries you most, and why?

No single right answer — the discussion is the point.

Lab. Find all nine in the finished CyberTravels tree (checkpoint A2.5) — a file for each — and count how many you placed.

A1.0What an agent is, and what you are about to build10 min

Key idea

Map the system before arguing about its security. The edges where trust changes are where every control will go.

Prompt to Claude

Run lesson A1.0's checkpoint diff, then draw me a simple diagram of
CyberTravels' components and mark which edges cross a trust boundary.

Expected output

9 components, 8 present. egress is absent, and that absence is a finding rather than a gap.

Project the component table. It names, for each component, the file the learner writes, the lesson that builds it and the skill that checks it.

Worth saying out loud: it is not nine components to nine skills, and the page says so. One skill covers four of them, and egress has none, because you cannot check a component nobody built.

Debrief question

Why mark a box that doesn't exist?

Answer. So nobody later argues about controls for a component nobody built.

Lab. Map the architecture you are about to build, and mark where trust changes.

A1.1The loop — model, tools, and the step that turns text into an action15 min
Risk

A loop with no verifier accepts whatever the model says it did, and a demo that 'works' has never been checked.

Control

Plan, act, verify — with the verifier independent of the thing it checks.

Key idea

The loop's third stage is the one most systems skip. Plan, act, verify — with the verifier independent of the model.

Prompt to Claude

Open cybertravels/runtime.py, show me _verify_result, and run the two refund
checks from lesson A1.1 (asked 140, got 1400; asked 140, got 140).

Expected output

First check prints asked to refund 140, resource server refunded 1400. Second prints None, which in this function means nothing wrong here.

Your turn — predict first. Replace _verify_result's body with return None and rerun. The 1400 refund now passes silently. Point out what the page points out: nothing errored, no span says anything is wrong, and the trace is tidier than before. A reviewer reading it sees a clean run.

Debrief question

Why not just ask the model whether its answer was right?

Answer. That is a second opinion, not a verification.

Lab. Build the loop and add the independent verifier that decides what it may accept.

A1.2Tools over MCP — a resource server, and why it is a separate process15 min
Risk

Tools called in-process share the agent's authority by default, and there is no place left to put a check.

Control

A resource server per trust domain, each with its own audience.

Key idea

A tool called in-process shares the agent's authority, leaving nowhere to put a check. One resource server per trust domain, each with its own audience.

Prompt to Claude

Install cybertravels/requirements.txt, then print config.TOOL_POLICY as in
lesson A1.2 and explain the audience and HIGH RISK columns.

Expected output

7 tools: 5 mcp:internal, 2 mcp:vendor. 2 marked HIGH RISK — cancel_booking and issue_refund.

Teaching moment, now on the page. Starting an MCP server shows a blank cursor and nothing else. A1.2 says so explicitly: "It will look like nothing happened… silence means it is running and waiting." Without that line this is ten minutes of learners thinking they broke it.

Debrief question

A tool's description says read-only. Should you believe it?

Answer. No. Annotations are hints, not guarantees, and B1.9 is the lesson on what that enables.

Lab. Stand up both MCP servers and list their tools from the client.

A1.3Identity — the human, the workload, and the call10 min
Risk

A shared service-account key makes every action look identical in the log, and no investigation can name who caused one.

Control

A workload identity per agent, and a session token for the human that grants nothing downstream.

Key idea

Three principals in every action: the human who asked, the workload that acted, and the individual call.

Prompt to Claude

Mint Dana's user token and the workflow agent's token as in lesson A1.3,
decode both, and compare them side by side.

Expected output

Two different kinds of identity. Dana's token carries exactly one scope, agent:invoke — she may ask an agent to act, not act herself.

Introduce the cast here. The page opens with it now, and every example to the end of Module 3 uses these three people.

Debrief question

Three principals: the human, the workload, the call. Which question can't you answer if you only log one?

No single right answer — the discussion is the point.

Lab. Mint both tokens and read the claims that make them different.

A1.4Delegation — one token per action15 min
Risk

An agent holding a long-lived token with every scope is one prompt away from using all of them.

Control

Per-action exchange, least privilege keyed to the human's role, enforced at the resource server.

Key idea

A long-lived, all-scope token is one ambiguous sentence from misuse. Exchange a token per action, keyed to the human's role.

Prompt to Claude

Run lesson A1.4's loop that asks for payments:refund as Dana and then as Priya.
Explain why the results differ.

Expected output

dana -> REFUSED: role 'traveller' may not delegate 'payments:refund' and priya -> minted.

The key point, and the page now lists all three. Dana's request stopped before the model was asked anything, before any booking was looked up, and before the payment server was contacted at all. Two independent things must fail, and the second does not depend on the model.

Debrief question

Is Dana's refusal a broken button?

Answer. No: same code, same request, different person.

Lab. Exchange a token, then watch a traveller's role refuse to delegate a refund scope.

1:50–2:00 · Break

2:00–2:45 · Memory, peers, and stopping the loop

The theme is that untrusted text travels — into memory, between agents, and round a loop that never stops. Each lab shows the label or the limit that contains it.

A1.5Memory — what it remembers, and where that came from15 min
Risk

Text an agent read becomes a fact an agent learned, and one vendor sentence outlives the request that fetched it.

Control

Origin travels with content; recall never crosses an owner boundary; delete and export both exist.

Key idea

Text an agent read becomes a fact it learned, unless the origin travels with it.

Prompt to Claude

Run lesson A1.5's memory example: save the policy sentence and the
vendor-document sentence for owner 1, then print the prompt block for
owner 1 and owner 2.

Expected output

Owner 1 shows [trusted, origin=policy] and [UNTRUSTED, origin=vendor-document]. Owner 2 prints '' — an empty string.

Two things to point at, in this order. The labels survived the write, so the two sentences do not arrive with equal weight. And Priya's block is empty: same call, different owner, nothing shared. The page's words — "closed here by storage, not by cleverness."

Your turn — predict first. "If we drop the origin column, what does the model see?" Both sentences now carry equal weight. Nothing errors.

Debrief question

Why is the label the control, rather than an instruction telling the model to ignore untrusted text?

Answer. An instruction is a request; a label is structure.

Lab. Write a vendor sentence into memory and watch it come back labelled untrusted.

A1.6Agent to agent — handing work over without laundering authority15 min
Risk

A peer's message read as a colleague's instruction turns one injected document into four compromised agents.

Control

Signed envelopes, the human carried through every hop, and a ceiling on hops.

Key idea

A peer's message read as a colleague's instruction turns one poisoned document into four compromised agents.

Prompt to Claude

Run both experiments in lesson A1.6: tamper with a signed envelope, then
forward a message in a loop. Explain each error.

Expected output

Experiment 1 raises A2AError: signature does not match. Experiment 2 prints hops 1, 2, 3 — each still carrying dana and tr-1 — then stops with hop ceiling reached (4).

Frame both errors as the result, which the page now does up front: "in both cases, the error message is the result you are looking for, not a sign something went wrong."

Your turn. Replace forward(...) with a fresh envelope(...). Hops print 0 forever and the ceiling never fires. This bug really shipped for one release — nothing incremented the counter, so the ceiling was unreachable. Only a test that forwards for real would have caught it.

Debrief question

The error message was the result we wanted. Where else in security is a refusal the success case?

No single right answer — the discussion is the point.

Lab. Forge a peer message and watch verification refuse it.

A1.7The human gate, and the budget that stops the loop15 min
Risk

An unbounded loop against an impossible task spends until somebody notices, and a gate nobody can approve fast enough is a gate that gets removed.

Control

High-risk actions gated on a named human; budgets that bind and are recorded when they bind.

Key idea

Two ceilings on one loop, failing in opposite directions: a gate nobody can keep up with, and a budget that spends until somebody notices.

Prompt to Claude

Run lesson A1.7's budget snippet and explain what the final word it prints means.

Expected output

8 12, then 12 tool_calls. The run ends saying which limit it hit — an unfinished answer that admits it is unfinished.

Trainer demo, in the browser. Run ./cybertravels/run.sh, sign in as Dana, ask to cancel CT-4417. The page's steps are numbered: watch it stop and name the scope it wants, approve once, then ask again and refuse. Both decisions are recorded.

Discussion. At 10 approvals a day a person reads each one; at 400 they approve the queue. Coverage stays at 100% while real review falls to zero. That is B3.9.

Debrief question

12 calls is a ceiling on the run. What stops all 12 hitting one traveller's booking?

Answer. Nothing yet. That is the per-target ceiling, and it is built in B3.4.

Lab. Approve one action, refuse another, then exhaust the budget on purpose.

2:45–3:40 · Harness engineering

The agent works. This module asks whether anyone else could investigate it, and whether its scores mean anything. Frame the whole module with one scenario and keep returning to it: a traveller disputes a cancellation three weeks later, and the only log line says run completed.

A2.0Why a demo is not a system — the harness around the loop10 min
Risk

A demo promoted to production carries none of the machinery an incident needs, and the first investigation discovers that at the worst moment.

Control

Spans, an audit trail, an evaluation, and a stop — built before they are needed.

Key idea

Measure the gap before building anything.

Prompt to Claude

Run the audit-answerability-check skill from lesson A2.0 and show me which of
the three questions the sample log cannot answer.

Expected output

answerable_count: 0 — all 3 unanswerable. Every row says agent-svc, and there is no motivating input at all.

Keep two triples apart, which the page now does explicitly. The three capabilities the chapter builds — a trace, an audit trail, an evaluation — are not the three questions the skill scores. The skill asks: which human, what motivated it, which hop. It is a number out of 3.

Debrief question

Is the agent identity the same as the principal?

Answer. No. It answers what ran, never who wanted it.

Lab. List what your run currently cannot tell an operator.

A2.1Observability — the run as spans10 min
Risk

A trace holding only successful calls hides exactly the events worth alerting on, and a token pasted into a span is a credential in the log pipeline.

Control

One trace id joining the reasoning to the audit row; refusals as first-class spans.

Key idea

A trace of only successes hides what is worth alerting on, and a token pasted into a span is a leaked credential.

Prompt to Claude

List the 12 span kinds in cybertravels/observability.py and explain why
start and done matter.

Expected output

12 span kinds: thought, plan, approval, token_issued, denied, tool_result, final, budget, escalation, start, error, done. The four at the edges — start, error, final and done — are the ones a hand-rolled tracer leaves out, and they are what make a missing span visible.

Four refusal points, four different incidents, and the page names all four: policy is a control working as designed; human is somebody saying no; verifier means the call was authorised, ran, and came back unacceptable; resource server means a token that should never have existed reached a boundary — that is the one that wakes people up.

Your turn. "What happens if we log the whole token instead of its claims?" The trace gets more useful, and the credential is now in every log backup.

Debrief question

A trace with no done span: is that a run still going, or a run that died?

Answer. You cannot tell, which is why the pair exists.

Lab. Emit a run's spans and join them to the audit log by trace id.

A2.2The audit trail, and the four questions it has to answer10 min
Risk

An append-only log the workload can still edit proves nothing, and one that records only successes cannot show what was attempted.

Control

Append-only storage, the delegation chain on every row, and refusals recorded alongside actions.

Key idea

Every audit row must answer four questions: which human, which workload, which call, and what motivated it. The fourth is almost always missing.

Prompt to Claude

Run the attribution-ledger-check skill from lesson A2.2 and explain question 4
in its output.

Expected output

4/4 answered, and question 4 reads roughly: the traveller asked about a double charge, but wiki/473 — a retrieved document, origin knowledge — is what triggered the DELETE.

Note the count changes. A2.0 scored out of three; this is out of four. The fourth question — which call, with its audience and scope — is the one A2.0's three did not include.

It is deliberately the same incident as A2.0, told by a record designed to answer.

Debrief question

Without question 4, how does this incident get closed?

Answer. "The agent misbehaved", which fixes nothing.

Lab. Put the four questions to your own audit rows and record which one fails.

A2.3Evaluating what you built, before anybody attacks it10 min
Risk

A suite everything passes measures nothing, and a score with no interval is a number that will move next week and nobody will know why.

Control

Cases that fail on the old build and pass on the new one, scored with intervals.

Key idea

A score needs an interval, cases that fail on the old build, and protection from dilution.

Prompt to Claude

Run the eval-suite-health-check skill from lesson A2.3. Then explain how adding
30 easy cases would change the aggregate score.

Expected output

Per-case rates with 95% intervals, for example INJ-01 0.055 (0.033, 0.077). Then the diluted aggregate, with the build unchanged and the skill saying so — "The build did not change. The number improved by 60%."

Debrief question

Conformance versus accuracy: an empty result matches every schema. Is it correct?

No single right answer — the discussion is the point.

Lab. Run the suite, then dilute it with easy cases and watch the score rise.

A2.4Evaluating the agent's behaviour — tool calls, outputs, and the model as judge15 min
Risk

"The agent is 90% accurate" with no denominator, no matcher named and no judge validation. Three different numbers can be quoted from one run, the most flattering is the easiest to compute, and an unvalidated judge is a second unmeasured model grading the first.

Control

Exact-match tool-call accuracy reported with its n and beside the two weaker matchers, output accuracy with unscoreable runs in their own column, and a judge whose agreement with ground truth is published before its verdicts are.

Key idea

Three matchers give three numbers from the same runs. Quote exact match, with n.

Prompt to Claude

Run skills/research/agent-eval-scoring/scripts/agent_eval_scoring.py and explain
why name-only and order-ignored scores are higher than exact match.

Expected output

Exact 0.500, name-only 0.667, order-ignored 0.667, n=6. Output accuracy 0.400 — 2 correct, 3 incorrect, 1 unscoreable.

Teaching moment. Name-only forgives R2, which refunded 1400 where 140 was owed. Order-ignored forgives R4, which booked the new seat before releasing the old one so the traveller held two. Different failures, hidden by each — which is why quoting one of them alone is worse than quoting neither.

If you used an older version of this guide: output accuracy is 0.400, not 0.600. The scorer previously used substring matching and scored R2's 1400 as correct, because "140" sits inside "1400.00" — the lesson was committing the error it teaches. It compares numbers as numbers now, and R2 fails both surfaces.

Debrief question

Someone says our agent is 90% accurate. What three things do you ask?

Answer. Accurate on which matcher, over how many runs, and who judged it?

Lab. Score six agent runs three ways, then check the judge against the runs whose answer you already know.

A2.5What you have built — and every way it can now go wrong10 min
Risk

Builders who never see their own system described adversarially ship the same defect in the next one.

Control

The same architecture map, annotated with what an attacker reaches for at each edge.

Key idea

Blast radius = what one run can reach × how irreversible its actions are × how long until a human can stop it.

Prompt to Claude

Run the blast-radius-review skill from lesson A2.5 and explain which actions are
irreversible and which need human approval.

Expected output

A table of actions with reversibility and routing. 4 are irreversible — delete_row, send_email, issue_refund and rotate_credential — and 2 of those are also external: send_email and issue_refund. Those are the ones routed to human approval.

Say the thing that makes the handover land: nothing in the Function B column is a criticism of their build. It is what the build looks like to somebody who wants it to fail.

Debrief question

Which number decides how much autonomy this agent can be given?

Answer. The blast radius, which is why it is the last thing Function A produces and the first thing Function B argues with.

Lab. Compute the blast radius of the agent you just built.

✓Capstone and marking

  1. Mark the guess sheet. Run the A2.5 checkpoint into work/finished, open the folder, and tick each correct guess from Module 0. Pairs share one thing they got wrong and what they learned. All nine words now have a file, and they wrote every one.
  2. One unguided task — pick one. Make the agent refuse an action it currently allows and name which of the four refusal points you used. Or name a tenth word CyberTravels has that the list does not, and its file. Or cut the blast radius by one irreversible action without turning the feature off. Claude may be used here, but the learner explains the result.
  3. Three answers, in their own words, without re-reading the pages. What can your agent do? What stops it doing something it should not, in the order a request meets them? What would you look at first if it misbehaved at 3am?

Marking the three answers

The questionWhat a good answer contains
What can it do?Names the tools, the high-risk ones, and that it acts on behalf of a named human rather than as itself.
What stops it?In order: delegation refused by role → human gate on irreversible actions → resource server verifies the token → verifier checks the result → budget stops the loop. Credit any answer that gets the order right even if a name is fuzzy; the order is the understanding.
Where would you look at 3am?The trace, by trace id. Then the audit rows, starting with any denied span — and which of the four places it was denied, because that alone tells you whether it is a control working or a credential that should not exist.

◉Pitfalls, and what to do

PitfallWhat to do
Learners accept Claude's narration as the resultInsist they find the actual printed output and compare it against this guide. This is the course's own lesson applied to the course.
"No model configured" read as failureReframe it every time: the program refused to make something up.
Edits from a "Your turn" block the next lessonThe run prints stopped, not FAILED, says the edits are safe, and offers two choices. Use --out for a fresh folder; do not let learners --force away work they wanted to keep.
Rushing past predictionsThe predict-then-run step is where the learning happens. Protect the time even if a lab finishes early.
Turning it into an attack classFunction A has no adversary by design. Park attack questions for Function B — that is what the parking lot is for.
An expected output here not matching the runTrust the run, not this guide, and correct the source. Every number on this page is generated from the tree for exactly this reason, but a prompt's wording can still drift.
